# Reagent developer guide

## When to use this skill

- Creating a new Reagent project from scratch
- Writing `.rg` protocol files
- Designing multi-agent systems with Reagent
- Setting up agent definitions, roles, and native modules
- Compiling, running, and debugging Reagent projects
- Working with the TypeScript Reagent Controller (the only first-class runtime today) and the `[py]`-zone executor scaffolding under `runtime/ts/zone-execs/py/`

- Understanding current cluster/control-plane workflows for Reagent projects

## What is Reagent

Reagent is a **meta-language** for agentic/distributed protocols. It describes the choreography of agents, messages, and control flow. Actual computation happens inside **agent zones** written in a **host language** (`ts`, `py`, `kt`).

Core philosophy:
- **Protocols are first-class**: coordination logic is explicit, debuggable, composable
- **Zones are host code**: real TypeScript (executed natively) or `[py]`/`[kt]` zone bodies dispatched to their respective zone executors
- **Examples-first design**: the language evolves from concrete usage patterns
- **Two-layer architecture**: protocol choreography (Reagent) + agent behavior (host language)

## Project structure

A Reagent project has this layout:

```
my-project/
  reagent.json              — project manifest
  protocols/                — .rg protocol files
  agents/                   — per-agent folders
    my-agent/
      agent.json            — agent manifest
      impl.ts               — native module / I/O wrapper for `$agent`
  run_node.ts               — project runner (TypeScript)
  out/                      — compiled IR (generated by `reagent build`)
```

Create with: `cd projects/reagent && node lang/dist/cli.js init path/to/my-project`

### reagent.json

```json
{
  "name": "my-project",
  "version": "0.1.0",
  "description": "What this project does",
  "protocols": ["protocols/**/*.rg"],
  "agents": ["agents/*/agent.json"]
}
```

### Agent manifest (agent.json)

Binds a native module to an agent:

```json
{
  "name": "MyAgent",
  "role": "MyRole",
  "module": "./impl.ts",
  "config": {}
}
```

The module's export is injected as `$agent` in all zone bodies for that agent.

## Language quick reference

For authoritative syntax, always check `projects/reagent/docs/current/02-lang-spec.md`.
This section is only a practical memory aid.

### Protocol header

```rg
protocol Name {
  participants: roleA [py] static single initiator, roleB [ts]

  trigger on invoke with InputMessage
  trigger on event "topic.name" with InputMessage
  trigger on cron "0 9 * * MON"

  ...body...
}
```

- participants declare roles, host language, and optional modifiers
- `initiator` is a participant modifier, not a separate directive
- triggers define the protocol entry surface
- for cron and event triggers, resolve policies may be needed inside the trigger body

### Message step

```rg
sender --> receiver: MessageName = {
  onSend { /* sender's host code */ }
  onReceive { /* receiver's host code */ }
}
```

- `onSend` runs before send, `onReceive` runs after receive
- `$ctx.msg` is available in both hooks
- Hooks are optional

### Agent zone (standalone)

```rg
roleName {
  // host-language code
  // has access to $ctx, $self, $flow, reagent, $agent
}
```

### Control flow

```rg
// Loop (guard is REQUIRED)
loop (true) { ... }
loop ($ctx.count < 10) { ... }

// Alt (expression guard)
alt ($ctx.done == true) {
  ...when true...
} else ($ctx.other) {
  ...else branch...
}

// Alt (message guard)
alt (A --> B: Msg1) {
  ...branch 1...
} else (A --> B: Msg2) {
  ...branch 2...
}

// Parallel
par {
  ...branch 1...
} and {
  ...branch 2...
}

// Wait
wait 500ms

// Try/catch
try {
  ...body...
} catch ErrorLabel {
  ...handler...
}
```

### Protocol composition

```rg
// Synchronous child protocol call
roleA invokes ChildProtocol($ctx.input)

// Async invoke
roleA async invokes ChildProtocol($ctx.input)

// Role spawn
roleA spawns WorkerRole({ task: $ctx.input.task }) as worker

// Dynamic multicast
scatter ($flow.items as itemRole) {
  ...body executed per item...
}
```

### Message type definitions

```rg
message RequestData {
  query: string
  limit: number
}

message ResponseData {
  results: any[]
  total: number
}
```

Message types are used in protocol steps (`sender --> receiver: MessageType`) and as protocol input types.

### Role and agent definitions

```rg
role MyRole [py] {
  plays Proto1 as roleA
  plays Proto2 as roleB

  init {
    $self.state = {}
  }

  on protocolCompleted(Proto1) {
    // lifecycle handler
  }
}

agent MyAgent runs MyRole
```

### Runtime bindings in zones

| Binding | Scope | Purpose |
|---|---|---|
| `$ctx` | Per-role, per-protocol-instance | Working memory (isolated per role) |
| `$flow` | Propagated with messages | Data that travels with message flow |
| `$self` | Per-role, persistent | State that survives across protocol instances |
| `reagent` | Global | Runtime library: `emit`, `invoke`, `spawn`, `return`, `break` |
| `$agent` | Per-agent (optional) | Native module I/O (from `agent.json` manifest) |

### Async zones

If zone code contains `await`, the compiler automatically marks it as async.
No special syntax needed.

```
commander {
  $ctx.result = await $agent.think($ctx.prompt)
}
```

## Design patterns

### 1. Coordinator-as-protocol

An ephemeral role that owns the environment loop, not a domain entity.
Its `$agent` wraps the environment (I/O only).

```rg
protocol GameLoop {
  participants: coordinator [py] initiator, entity [py] dynamic many
  trigger on invoke with GameStart

  loop (true) {
    coordinator {
      $flow.obs = await $agent.observe()
    }
    scatter ($flow.agentIds as entity) {
      coordinator --> entity: Observation = { ... }
      entity --> coordinator: Action = { ... }
    }
    coordinator {
      await $agent.step($flow.actions)
    }
  }
}
```

### 2. Thin `$agent`, fat zones

`$agent` is a **pure I/O wrapper** — no decision logic. All reasoning,
state management, and coordination live in zone code.

Good:
```python
# $agent module — I/O only
class LLMAgentIO:
    async def think(self, prompt):
        return await self.llm.call(prompt)
```

```
// Zone code — all logic here
commander {
  $ctx.prompt = buildPrompt($self.worldModel, $self.teamStatus)
  $ctx.strategy = await $agent.think($ctx.prompt)
  $self.activeGoals.push($ctx.strategy)
}
```

Bad: putting decision logic in the native module.

### 3. Two temporal scales

Tick protocols (synchronous, per-step) coexist with behavioral protocols
(long-running, cross-tick). Decoupled via `$self.currentGoal`:

- **Tick protocol**: reads `$self.currentGoal`, translates to concrete action
- **Behavioral protocol**: sets `$self.currentGoal` based on strategic reasoning
- **Strategic protocol**: uses LLM to decide which behavioral protocol to invoke

### 4. Goal-based action translation

```
entity {
  goal = $self.currentGoal || { type: "idle" }
  $ctx.action = translateGoalToAction(goal, $ctx.msg.obs)
}
```

Behavioral protocols write goals, tick-level zones read them.

### 5. Scatter/gather for fan-out

```rg
scatter ($flow.agentIds as entity) {
  coordinator --> entity: ObsUpdate = {
    onSend { $ctx.msg.obs = $flow.observations[$flow._scatterIdx] }
  }
  entity --> coordinator: ActionResp = {
    onReceive { $flow.actions.push($ctx.msg.action) }
  }
}
```

### 6. Polling with wait + alt

For long-running protocols that need to check a condition periodically:

```rg
loop (true) {
  wait 500ms

  agent {
    $ctx.done = $self.goalStatus == "completed"
  }

  alt ($ctx.done == true) {
    agent --> commander: Result = { ... }
    agent { reagent.break() }
  }
}
```

## Syntax gotchas

1. **`agent` is a reserved keyword** — cannot be used as a participant name.
   Use `entity`, `member`, `worker`, `survivor`, etc.

2. **`loop` requires a guard** — `loop { }` is invalid. Use `loop (true) { }`.

3. **`alt` uses parenthesized guards** — `alt [expr]` is invalid.
   Use `alt (expr) { } else (expr) { }`.

4. **Zone code is raw text** — the Reagent parser only balances braces.
   It does not parse the host language inside zones.

5. **Zones of different roles cannot be adjacent** — there must be a message
   step between zones of different participants.

6. **`[*]` is the wildcard lang tag** — used when a role can be implemented in any language.

7. **Message-guard alt** — `alt (A --> B: Msg1) { } else (A --> B: Msg2) { }`
   uses message-based XOR.

8. **Async zones are auto-detected** — if zone code contains `await`, the compiler
   marks it async. No special syntax needed.

## Compilation

### Compile a single file

```bash
cd projects/reagent
node lang/dist/cli.js compile protocols/my-protocol.rg out/my-protocol
```

### Build entire project (preferred)

```bash
cd my-project
node /path/to/projects/reagent/lang/dist/cli.js build .
```

Or from within a project that has `reagent.json`:

```bash
cd projects/reagent && node lang/dist/cli.js build examples/projects/auction-sim
```

Reads `reagent.json`, compiles all matched protocols, generates:
- Per-role IR JSON files (`Auction.seller.ir.json`, `Auction.buyer.ir.json`)
- Per-role Role IR files (`SellerRole.role.json`)
- Per-agent Agent IR files (`Buyer1.agent.json`)
- `deployment.json` (agent→role→graph mappings)
- `messages.json` (message schemas)
- `source-map.json` (debug/source mapping)
- Updates `reagent.lock` (version tracking)

### Verify (TLA+ model checking)

```bash
cd projects/reagent
node lang/dist/cli.js verify protocols/my-protocol.rg
```

Compiles to IR → generates TLA+ spec → runs TLC model checker (if on PATH).
Checks deadlock freedom and protocol completion. If TLC is not installed,
generates `.tla` + `.cfg` files for manual verification.

### Deploy to the control plane

```bash
reagent-lang deploy [--ros-url ws://127.0.0.1:18789]
```

Builds, creates a deploy payload, and submits it to the current control-plane entrypoint.

Architecturally, the current canonical tool-facing API is `AdminClient`, backed by:
- `StateStore`
- node registrations in `/nodes/*`
- per-node `NodeControlEndpoint`s

Treat old ROS terminology as historical naming, not as the target architecture.

## Running

Reagent runs protocols on the **TypeScript Reagent Controller (RC)**. The
previously parallel Python runtime has been retired; only the `[py]`-zone
executor remains under `runtime/ts/zone-execs/py/` as RC virtual-language
scaffolding (see [`retire-python-runtime.md`](../../../projects/unin/reagent/docs/future/retire-python-runtime.md)).

### Running from the terminal

```bash
node lang/dist/cli.js build .       # compile (only needed after .rg changes)
npx tsx run_node.ts                 # run via the project's TS runner
```

For projects without a dedicated runner, bootstrap an RC inline from the
package surface (see `runtime/ts/src/main.ts` and the `auction-sim` example
under `examples/projects/auction-sim/run_node.ts`).

### Running from the IDE (▶ button)

With a `.rg` file open, click the **▶ play button** in the editor title bar or
run `Reagent: Run Protocol` from the command palette. The extension runs the
protocol in-process using the TypeScript runtime. Output appears in the
**Reagent Run** output channel.

### Running in cluster/state-store mode

Typical current shape:
1. start or reuse shared infra such as etcd and, when needed, the message plane
2. start one or more runtime hosts (`mcp-gate`, local nodes, test hosts, or wrapper-based live agents)
3. deploy through tool-side control-plane APIs
4. inspect nodes and agents through cluster state
5. trigger protocols from tools or MCP clients

### Edit-run cycle for agent code

1. **Edit** `agents/<name>/impl.ts` — change decision logic
2. **Run** via the IDE ▶ button or `npx tsx run_node.ts` — no recompile needed
3. **Iterate** — only recompile when `.rg` protocol changes

## IDE features (Reagent VSCode extension)

### Diagram views

- **Protocol Diagram** (⎅ icon in `.rg` file title bar): sequence diagram + state machine for the current protocol. Includes a **trigger bar** that shows agents available to initiate the protocol when connected to a cluster.
- **Project Diagram** (`Reagent: Open Project Diagram`): agents → roles → protocols overview for the entire project.

### Cluster panel

The **Reagent Cluster** tree view (sidebar) shows:
- Connected nodes (with status)
- Deployed agents (per-node and flat)
- Active protocols (with bound agents)

**Navigation**: clicking a tree item opens the relevant view:
- **Agent** → opens the project diagram
- **Protocol** → opens the `.rg` source file + protocol diagram

### Trigger bar (in protocol diagram view)

When connected to a cluster, the trigger bar at the top of the protocol diagram shows:
- Connection status
- Agents that can initiate the current protocol (filtered by `isInitiator` role, with fallback to all matching agents)
- Agent selector dropdown + "Trigger" button to start a protocol instance

## Debugging

### Cluster/runtime debug session (TS runtime)

For protocol-level debugging with breakpoints on send/receive/action states:

1. start the relevant node/runtime host
2. Open a `.rg` file
3. `Cmd+Shift+P` → `Reagent: Start Debug Session`

Shows trace timeline, agent state, held messages.

This path currently targets the TypeScript runtime/control-plane path.

## Runtime setup (advanced)

### TypeScript RC

```typescript
const factory = new ManagedBehaviorFactory();
const rc = new ReagentController({
  nodeId: "my-node",
  behaviorFactory: factory,
});

rc.deployAgentTemplate("MyAgent", roleIR, graphs, extras);
rc.createAgentFromTemplate("MyAgent", { start: true });
await rc.start();
rc.triggerProtocol("MyAgent", { instanceId, protocolName, input, roleToAgent: deployment.roleToAgent });
```

### MCP Gate and live-agent hosts

Current practical split:

- direct MCP clients such as Codex often launch `mcp-gate` directly using a plain `RuntimeConfig`
- Claude-backed live agents launch through `runtime/agents/claude/live-agent.ts`
- wrapper node configs embed `RuntimeConfig` plus node-kind-specific settings

Direct `mcp-gate` launch shape:

```json
{
  "mcpServers": {
    "reagent": {
      "command": "node",
      "args": ["mcp-gate.js", "--runtime-config", "./my-agent.runtime.json"]
    }
  }
}
```

Claude wrapper node config shape:

```json
{
  "kind": "claude_live_agent_node",
  "runtime": { "...": "RuntimeConfig" },
  "agent": { "name": "WorkerAgent", "roles": ["WorkerRole"] },
  "claude": { "...": "Claude-specific settings" }
}
```

Do not push Claude-specific settings into core `RuntimeConfig`.

## Four integration modes

All current agent-hosting paths fit into four practical modes:

### 1. Managed mode

- factory: `ManagedBehaviorFactory`
- execution: `AgentShellImpl` + `RoleRun`
- use when: most `.rg` projects with in-protocol zone logic

### 2. Custom agent mode

- factory: `CustomBehaviorFactory`
- execution: user `AgentBehavior` + `RoleRun`
- use when: agent logic is too complex or too externalized for zone-only code

### 3. Message Gate mode

- factory: `GateBehaviorFactory`
- transport: WS / stdio / HTTP push-style event delivery
- use when: isolated external processes or polyglot agents

### 4. MCP Gate mode

- host: `mcp-gate`
- adapter path: `McpAgentAdapter` + `ReagentMcpServer`
- use when: LLM agents or other MCP-capable clients

## OTel integration

Two instrumentation hooks for production observability:

- `createOTelInterceptor(tracer?)` — message-level spans
- `createOTelTraceHook(tracer?)` — trace/event-level spans

```typescript
const rc = new ReagentController({
  nodeId: "my-node",
  behaviorFactory: new ManagedBehaviorFactory(),
  interceptors: [createOTelInterceptor()],
  traceHook: createOTelTraceHook(),
});
```

All OTel instrumentation lives in the TS runtime; no parallel Python wiring is shipped.

## Checklist for new Reagent project

1. **Scaffold**: `cd projects/reagent && node lang/dist/cli.js init path/to/my-project`
2. **Design protocols** as `.rg` files in `protocols/`
3. **Use `02-lang-spec.md`** as the syntax authority while writing them
4. **Define roles** with `plays` bindings and `init` / lifecycle handlers as needed
5. **Define agents** with `runs` bindings
5. **Create per-agent folders** in `agents/` if native modules needed:
   - `agents/my-agent/agent.json` — binds role to native module
   - `agents/my-agent/impl.ts` — thin I/O wrapper (`$agent`)
6. **Create `run_node.ts`** at the project root as the canonical entry point
7. **Compile**: `node lang/dist/cli.js build .`
8. **Verify in IDE**: use syntax highlighting, diagrams, symbols, and cluster views
9. **Run**: `npx tsx run_node.ts`, or via the IDE ▶ button, or a host such as `mcp-gate`
10. **Debug**: use the current TS runtime debug path
11. **Deploy to cluster** (optional): use current state-store/control-plane workflow
12. **Iterate**: edit host code or modules, rebuild only when `.rg` or compiled artifacts changed
